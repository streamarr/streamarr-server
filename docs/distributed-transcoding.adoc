= Distributed Transcoding

The default Compose deployment starts one server and one colocated worker.
Workers perform all transcoding, remuxing, and background media probes.
The server does not execute FFmpeg.

Workers connect outward for control and upload segments over their worker session.
They read media through an administrator-defined source namespace and never connect to PostgreSQL.
The standalone worker's inbound management port serves health checks. The server does not use it to dispatch work.

== Worker connections

The server exposes one plaintext gRPC listener.
`STREAMING_WORKER_SESSION_ADDRESS` defaults to `127.0.0.1` and `STREAMING_WORKER_SESSION_PORT` defaults to `9090`.
The server can start without connected workers. Probes stay pending until a capable worker connects.

For colocated workers, keep the loopback address and share the server's network namespace.
Every process that can reach this listener is trusted.
Reusing a worker UUID replaces its previous connection and abandons that connection's active jobs.
Share the namespace only with trusted processes.

For distributed Kubernetes workers, set the address to `0.0.0.0` and protect port `9090` with the service mesh.
The example requires Istio sidecar interception, strict mutual TLS on the worker port, and authorization for the dedicated worker ServiceAccount.
The server does not load certificates or inspect forwarded identity headers.
Keep both inbound and outbound worker traffic inside the mesh.

[IMPORTANT]
====
Binding the worker listener to a network interface requires the mesh policies to be enforced.
Plaintext traffic to the Pod IP must also be rejected.
The mesh authenticates the worker ServiceAccount. The worker UUID remains a claimed instance identifier.
An authorized worker can claim another worker's UUID. Workers in that role therefore share trust.
====

== Probe capacity and playback slots

Each worker grants four separate capacities when it connects, as https://github.com/streamarr/streamarr-adr/blob/main/adr/0032-media-file-probe-results-are-persisted.adoc[ADR 0032] decides:

[cols="1,2,2"]
|===
|Capacity |Work |Value

|Playback slots
|Job attempts
|`TRANSCODE_WORKER_SLOTS` on the worker. The default is `1`.

|Playback probe capacity
|Probes that a playback request waits for
|`2`

|Background probe capacity
|Every other probe, such as the probes of a library scan
|Adaptive. It starts at `4` and stays between `1` and the processors available to the worker's JVM.

|Keyframe packet scan capacity
|Keyframe packet scans
|`0` while the worker runs a job attempt, and `1` once no job attempt has run for 30 seconds.
|===

A probe never takes a playback slot, and a job attempt never takes a probe unit.
A stream session can therefore start on a worker while a library scan probes many files on the same worker.
A playback probe can also use a free background unit, but a background probe never uses a playback probe unit.
A playback probe therefore starts even while a scan uses every background unit.

The worker adapts its background probe capacity to the host.
The capacity grows by one when a probe ends while at least half of the capacity was in use.
It halves when a job attempt starts.
It also halves when a job attempt produces media slower than 2.10 times real time, and again every 15 seconds while the attempt stays slow.
After it halves, the capacity does not grow for 30 seconds.
Background probes and keyframe packet scans run at the lowest CPU priority, so playback keeps the processors that it needs.
In Kubernetes, the worker's CPU request sets the processors that its JVM counts. See <<_kubernetes>>.

Set `TRANSCODE_WORKER_PROBE_CAPACITY` on the worker to fix the background probe capacity at a positive number.
A fixed capacity never grows or halves.
Fix it when the worker shares its host with other work that the worker cannot see, or when the worker should use fewer processors than its JVM reports.
The other probe capacities have no setting.

A worker reports a new capacity during its session, and the server sends new probes against the latest values.
Probes that already run keep running when a capacity drops.
When a probe reaches a worker that has just lowered the probe's capacity, the worker refuses the probe before it starts.
The probe then stays pending without a failure, and any worker with a free unit can take it.

The server claims a due probe only when a compatible worker has a free unit of the probe's capacity.
Playback probes are claimed ahead of every other probe.
The server sends a playback probe to a worker with a free playback probe unit first.
A probe that waits for capacity stays pending without a failure.
When a probe finishes, the next due probe starts within `PROBE_POLLING_INTERVAL`, which defaults to `1s`.
One server runs at most `PROBE_SCHEDULER_THREADS` probes at once, 128 by default, and at most `PROBE_KEYFRAME_PACKET_SCAN_SCHEDULER_THREADS` keyframe packet scans, 16 by default.
Raise `PROBE_SCHEDULER_THREADS` when the connected workers grant more probe units than that.
For workers sharing one NAS, start with `PROBE_KEYFRAME_PACKET_SCAN_SCHEDULER_THREADS=1` on the server and raise it as storage throughput allows.
This positive ceiling limits scans across all workers connected to that server; each worker's free scan units can limit them further.
It does not limit ordinary probes or playback reads, and is not a storage bandwidth limit.
A probe that waits for a worker's result holds no database connection, so the setting needs no larger connection pool.

A worker that grants a background probe capacity of `0` receives no background probes, and the server logs a warning when that worker connects.
When no connected worker can run probes, due probes stay pending without a failure.
They start at the first poll after a worker that can run them connects.
A scan waits for its probes until then.

The server logs each capacity and the playback slots of each worker that connects.
While a scan waits for its probes, the server logs the scan's progress every 30 seconds: the probes saved, the probes waiting, the files probed per second, and each probe capacity of the connected workers.
The progress line becomes a warning while no connected worker can run probes.
When the server defers probes because every compatible worker is busy or no compatible worker is connected, it logs a warning with the reason and the number of deferred probes.
The server logs that warning at most once a minute for each reason.

These metrics report the same facts:

* `streamarr.probes.capacity` reports the units of each capacity that a worker grants. It carries the `worker` and `kind` tags. The kind is `playback`, `background`, or `keyframe_packet_scan`.
* `streamarr.probes.running` reports the probes of each kind that run on a worker. It carries the same tags.
* `streamarr.probes.background_capacity_control` is `1` for each worker. Its `control` tag is `adaptive`, or `fixed` when `TRANSCODE_WORKER_PROBE_CAPACITY` sets the capacity.
* `streamarr.probes.waiting` reports the probes that running scans still wait for. A probe waits unclaimed while no worker has a free unit for it.
* `streamarr.probes.deferred` counts the probes that the server deferred after it claimed them. Its `reason` tag is `workers_busy`, `no_compatible_worker`, or `no_connected_worker` when no worker could take the probe at dispatch, and `no_free_capacity` when the worker refused the probe because it had just lowered the probe's capacity.
* `streamarr.probes.keyframe_packet_scan_failures` counts the keyframe packet scans that ran without a usable result. Its `reason` tag is `timed_out`, `no_keyframe_result`, or `contract_violation` when the worker's reply broke the worker contract.
* `streamarr.playback.probe_queue_latency` records queue latency for a claimed probe, from its earliest still-waiting playback request until execution starts. It includes scheduler polling, any remaining quiet period or retry backoff, and capacity waits, so a nonzero value alone does not establish capacity exhaustion. Requests that stop waiting before execution starts contribute no sample.
* `streamarr.playback.probe_wait` times how long a playback request waited for its file's probe outcome. Its `outcome` tag is `ready`, `probe_failed`, or `not_ready`.
* `streamarr.playback.probe_waits` reports the playback requests that wait for a probe now.
* `streamarr.streaming.playback_slots` and `streamarr.streaming.playback_slots_in_use` report each worker's playback slots and the job attempts that use them. They carry the `worker` tag.
* `streamarr.streaming.production_speed` reports the media seconds that a worker produced per second of production time, for each media segment it uploads. It carries the `worker` tag.
* `streamarr.streaming.capacity_refusals` counts the stream sessions refused for lack of capacity. Its `cause` tag is `no_connected_worker`, `no_free_worker_slot`, `no_free_configured_transcode_slot`, or `no_encoder_with_free_slot`.

== Media and health

Set `STREAMING_REMOTE_SOURCE_NAMESPACE_ID` and `STREAMING_REMOTE_SOURCE_ROOT` for the server's media mapping.
Configure the same namespace UUID on each worker with `TRANSCODE_WORKER_SOURCE_NAMESPACE_ID` and `TRANSCODE_WORKER_SOURCE_ROOT`.
Container paths may differ, but a relative key beneath each source root must identify the same media.
Mount media read-only.
Workers on different nodes need storage that supports those simultaneous mounts.
Workers need no writable output directory: FFmpeg writes fragmented MP4 to the worker over standard output (https://github.com/streamarr/streamarr-adr/blob/main/adr/0037-worker-delivers-fmp4-segments-from-ffmpeg-stdout.adoc[ADR 0037]).

Each segment is capped at 128 MiB. The server reserves at most 512 MiB of declared payload across active uploads; buffer growth, publication copies, and other server memory require additional heap headroom.
Workers budget 256 MiB of buffered output per execution slot, plus a 64 KiB read buffer per FFmpeg process. FFmpeg, pipe buffers, and gRPC use additional memory.
Deploy the server with the larger cap before deploying workers that produce larger segments.

Set `TRANSCODE_WORKER_FFPROBE_PATH` to the worker's ffprobe binary. It defaults to `ffprobe` on `PATH`.
`STREAMING_WORKER_SESSION_PROBE_TIMEOUT` bounds each probe on the server. It defaults to `1m`.
When playback asks for a file that has no probe outcome, the server moves the file's probe to the front of the queue and waits for the outcome.
`STREAMING_PROBE_WAIT_LIMIT` bounds that wait. It defaults to `15s`.
`GRAPHQL_HTTP_REQUEST_TIMEOUT` sets how long a GraphQL request over HTTP may run. It defaults to `30s`.
Keep the probe wait limit at most half of the request timeout, so the stream session can still start after the wait.
When the wait reaches the limit, `createStreamSession` returns `MediaFileProbeNotReadyError` and the probe keeps running.
`STREAMING_WORKER_SESSION_KEYFRAME_SCAN_TIMEOUT` bounds each keyframe packet scan on the server. It defaults to `30m`.
A packet scan reads every packet of the source's video stream, which takes longer than a probe on network storage.
A timeout requests worker cancellation and lets the scheduler retry.
After three packet scans of a source time out, report no keyframes, or get a worker reply that breaks the worker contract, the server stores its keyframes as unavailable, so playback encodes the source.
Packet scans run on a scheduler of their own, so they never take the threads that run probes.
Each cancel command carries a reason: the probe timeout, a server shutdown, or another reason.
When a probe or a packet scan reaches its timeout, the command carries the timeout reason.
When the server stops a probe while the server shuts down, the command carries the shutdown reason.
The worker learns of a timeout only from this reason.
The worker may lower its background probe capacity when probes reach the timeout, but not when a packet scan does (https://github.com/streamarr/streamarr-adr/blob/main/adr/0032-media-file-probe-results-are-persisted.adoc[ADR 0032]).
`STREAMING_WORKER_SESSION_PROBE_CANCELLATION_TIMEOUT` allows `5s` for the worker to acknowledge termination.
Until then, the probe keeps its unit of the worker's probe capacity.
A worker that misses this deadline is disconnected and fenced. Its other active jobs are abandoned and recover through the existing playback recovery path.
Closing a worker connection cancels its probes and waits for their native processes to terminate.
The server publishes no segment of an encode until the worker's start report names the encoder backend that the worker advertised.
`STREAMING_WORKER_SESSION_START_REPORT_TIMEOUT` bounds how long an upload waits for that report. It defaults to `10s`.
When the report names another backend, or does not arrive in time, the server refuses the upload.
An unresponsive filesystem can delay worker shutdown.
The server pings a worker after `STREAMING_WORKER_SESSION_KEEPALIVE_TIME` without hearing from it, and closes the connection when no acknowledgement arrives within `STREAMING_WORKER_SESSION_KEEPALIVE_TIMEOUT`.
Closing a dead worker's connection releases its playback slots, its probe capacity, and its upload reservations.
The time defaults to `30s` and must be at least `10s`, the shortest that gRPC allows. The timeout defaults to `10s`.

The server exposes Spring Boot probe groups at `/actuator/health/liveness` and `/actuator/health/readiness` on port `8080`.
The standalone Spring Boot worker exposes the same paths on port `9091`.
Worker readiness requires successful initialization and an accepted server session.
A busy worker stays ready. Losing its server session changes readiness without failing liveness.
The server still dispatches through the worker session using the advertised capabilities, playback slots, and probe capacity.

Keep worker availability out of the server's liveness and readiness groups.
A server with zero workers must remain reachable so workers can connect.
The Istio policy restricts only the worker port. HTTP and Kubernetes health probes retain their existing mesh policies.

== Filename encoding

The server and every worker must run under a UTF-8 locale.
Java converts filenames through the process locale, so an ASCII locale such as `POSIX` cannot open media whose names contain non-ASCII characters.
The server and worker images both default `LANG` to `C.UTF-8`, so neither the official Compose and Kubernetes settings nor a hand-written `docker run` needs to set a locale.
The default applies only when `LANG` is unset.
`LC_ALL` and `LC_CTYPE` override the default; if you set either, give it a UTF-8 value such as `C.UTF-8`.

The server logs a warning at startup when it does not read filenames as UTF-8.
On an affected worker, probes of non-ASCII names fail as `PROBE_FAILURE_SOURCE_UNAVAILABLE` and the worker log shows an `InvalidPathException`.
To recover, correct the locale and restart the affected process.
Do not rename media or rewrite library paths: stored filepath URIs preserve each filename's bytes, so the scheduler retries failed probes against the same files and playback can start again.

The server sends each worker a key relative to the source root, decoded from the stored URI.
The worker treats the key as literal filename text and never percent-decodes it, so a file named `100%23.mkv` keeps `%23` in its key.

== Docker Compose

The default worker uses `network_mode: service:streamarr-server` to reach the server over loopback.
Load the checked-in image from `worker-image.env` and set `STREAMARR_MEDIA_PATH` to the host media directory.
The pin file contains one unquoted `STREAMARR_WORKER_IMAGE=<image>@sha256:<digest>` assignment.
Blank lines and full-line comments are allowed. Do not add an `export` prefix or other assignments.
Set `STREAMARR_WORKER_IMAGE` in `.env` or the shell to override the pin.
Both containers mount the media directory read-only at `/media`, which is the library root inside the server.
`STREAMARR_WORKER_ID` and `STREAMARR_SOURCE_NAMESPACE_ID` override the example UUIDs.

[source,bash]
----
STREAMARR_MEDIA_PATH=/absolute/path/to/media docker compose \
  --env-file worker-image.env --env-file .env up -d
----

The worker uses its own Spring Boot image and normal entrypoint.
The server image contains neither the worker application nor FFmpeg.
To encode on an NVIDIA GPU, see <<_gpu_encoding>>.

== Kubernetes

link:../deploy/kubernetes/distributed-transcoding.yaml[The example manifest] creates the `streamarr` namespace with sidecar injection enabled, separate server and worker ServiceAccounts, one server replica, and two worker replicas.
It requires:

* an installed Istio sidecar control plane with the `cluster.local` trust domain
* a `streamarr-media` PersistentVolumeClaim in the `streamarr` namespace
* a `streamarr-runtime` Secret in that namespace with `datasource-url`, `datasource-username`, and `datasource-password`

Replace the server image placeholder with a verified immutable version.
The renderer uses the checked-in `worker-image.env` pin unless `STREAMARR_WORKER_IMAGE` overrides it.
Adapt the storage, source namespace, and runtime Secret.
If you change the Kubernetes namespace or mesh trust domain, update the authorized principal in the `AuthorizationPolicy` too.
The worker ID comes from the Pod UID. Scaling the Deployment produces distinct instance identifiers without per-replica configuration.

Port `9090` requires mesh mutual TLS and the `streamarr-transcode-worker` ServiceAccount.
Port `8080` retains its existing mesh and application access controls.
An ingress in front of port `8080` must pass WebSocket upgrades on `/graphql`. See link:graphql-subscriptions.adoc#_reverse_proxies[GraphQL Subscriptions].
If the namespace already has an allow policy, it must also permit the authorized worker's traffic to port `9090`.
Do not add exclusions for the worker port to the sidecar annotations.

Keep one server replica and `Recreate` replacement. Its worker and playback session registries are in memory.
Worker replicas may scale horizontally as long as each can read the configured media namespace.

Each worker requests two CPUs and sets no CPU limit, so it can use idle cores on its node.
Keep the request at two CPUs or more. At one CPU, the JVM runs virtual threads on a single carrier thread.
Without a CPU limit, the JVM counts every core on the node. JDK 19 and later ignore CPU shares, which carry the CPU request, when they count processors.
The manifest therefore passes the CPU request to the JVM as `-XX:ActiveProcessorCount` in `JAVA_TOOL_OPTIONS`.
Kubernetes rounds the request up to a whole core, so a request of `1500m` gives the JVM two processors.
The default probe capacity follows from that count. Raise the CPU request to raise it, or set `TRANSCODE_WORKER_PROBE_CAPACITY`.
Keep the CPU request. Without a request or a limit, the JVM counts every core on the node again.
The image appends its own JVM options to `JAVA_TOOL_OPTIONS`. Add other JVM options to the same value.
The processor count applies only to the JVM. FFmpeg still counts the node's cores.
A CPU request changed in place takes effect when the container restarts.

[source,bash]
----
python3 deploy/kubernetes/render-deployment.py > /tmp/streamarr-deployment.yaml
kubectl apply -f /tmp/streamarr-deployment.yaml
----

To encode on NVIDIA GPUs in worker pods, see <<_kubernetes_gpus>>.

== GPU encoding

The worker can encode video on an NVIDIA GPU.
Only NVIDIA GPUs work for now.
The worker image's FFmpeg has VAAPI, Quick Sync and AMF encoders, but the image lacks the libraries they load at run time: `libva`, the Intel media driver and AMD's `libamfrt64`.
Passing `/dev/dri` to the worker therefore leaves Intel and AMD encoding unavailable.
Without a usable GPU, the worker encodes H.264 with libx264, HEVC with libx265 and AV1 with libsvtav1.

=== Host prerequisites

Install these on each host that runs a worker:

* An NVIDIA driver for the GPU. Run `nvidia-smi` on the host to check that the driver sees the GPU.
* The https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html[NVIDIA Container Toolkit], configured for Docker. Run `sudo nvidia-ctk runtime configure --runtime=docker` and restart Docker.

FFmpeg's NVENC encoders load the driver's CUDA library and its video encode library.
The toolkit mounts the video encode library only for a container that requests the `video` driver capability.
Without a request, the toolkit mounts its default capabilities, `compute` and `utility`.
See https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/docker-specialized.html#driver-capabilities[Driver Capabilities].
Every example below requests `compute`, `video` and `utility`.
The worker uses `compute` and `video`. The `utility` capability adds `nvidia-smi` to the container for troubleshooting.

=== Docker Compose GPUs

Add a GPU reservation to the `transcode-worker` service in your Compose file:

[source#compose-nvidia-gpu,yaml]
----
services:
  transcode-worker:
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu, compute, video, utility]
----

Docker passes the `compute`, `video` and `utility` entries to the toolkit as `NVIDIA_DRIVER_CAPABILITIES`.
A reservation with only `[gpu]` can leave out the video encode library, because the toolkit then mounts only its defaults.
See https://docs.docker.com/compose/how-tos/gpu-support/[Enable GPU support] for the other reservation fields.

=== docker run GPUs

If you start the worker with `docker run`, add the `--gpus` option with the same capabilities and keep the worker's other options:

[source#docker-run-nvidia-gpu,bash]
----
docker run --gpus 'all,"capabilities=compute,video,utility"' ... "$STREAMARR_WORKER_IMAGE"
----

Some hosts give containers GPUs through the `nvidia` runtime and `NVIDIA_VISIBLE_DEVICES` instead of a GPU request.
On those hosts, also set `NVIDIA_DRIVER_CAPABILITIES=compute,video,utility` on the worker container.

=== Kubernetes GPUs

Worker nodes need the NVIDIA driver, the NVIDIA Container Toolkit configured for the node's container runtime, such as containerd, and the https://github.com/NVIDIA/k8s-device-plugin[NVIDIA device plugin].
The https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/index.html[NVIDIA GPU Operator] installs and configures all three.
The Docker setup in <<_host_prerequisites>> does not configure a Kubernetes node's container runtime.
Save this patch as `worker-gpu-patch.yaml`:

[source#kubernetes-nvidia-gpu,yaml]
----
apiVersion: apps/v1
kind: Deployment
metadata:
  name: streamarr-transcode-worker
spec:
  template:
    spec:
      containers:
        - name: worker
          env:
            - name: NVIDIA_DRIVER_CAPABILITIES
              value: compute,video,utility
          resources:
            limits:
              nvidia.com/gpu: 1
----

Apply the patch to the deployed worker:

[source,bash]
----
kubectl -n streamarr patch deployment streamarr-transcode-worker \
  --type strategic \
  --patch-file worker-gpu-patch.yaml
----

The patch adds the variable to the worker's existing environment and keeps its CPU request.
Each worker pod then needs a free GPU on its node.

=== Confirm GPU encoding

At startup, the worker encodes one test frame with each hardware encoder and logs the result in one line:

[source,bash]
----
docker compose logs transcode-worker | grep 'FFmpeg capabilities:'
----

On a working GPU, `GPU=true` and the encoder backends name NVENC encoders with `hardware=true`:

[source,text]
----
FFmpeg capabilities: GPU=true, encoders=[h264_nvenc, hevc_nvenc], accelerator=cuda,vaapi,qsv,drm,opencl,vulkan,amf, encoder backends=[EncoderBackend[codecFamily=H264, encoder=h264_nvenc, hardware=true], EncoderBackend[codecFamily=HEVC, encoder=hevc_nvenc, hardware=true], EncoderBackend[codecFamily=AV1, encoder=libsvtav1, hardware=false]]
----

The worker uses a hardware encoder only after its test encode succeeds.
An encoder that the GPU lacks fails the test encode, and that codec stays on its software encoder.
In the example, the GPU has no AV1 encoder, so AV1 stays on libsvtav1.
The worker runs the test encodes again only when it restarts.

If the line shows `GPU=false`, run `nvidia-smi` in the worker container, for example `docker compose exec transcode-worker nvidia-smi`.
If that command fails, the container has no GPU. Check the toolkit setup and the reservation.
If it lists the GPU, check that the request includes the `video` capability.

== Validate the mesh

link:../deploy/kubernetes/test/README.md[The isolated mesh test] creates a temporary kind cluster and runs the real worker-session service behind Istio.
Scripted clients isolate authorization checks. The required standalone worker image then probes media and uploads a transcode segment that FFmpeg decodes.
The test proves that a different ServiceAccount is denied and an unmeshed client cannot connect through either the Service or the direct Pod IP.
Ordinary HTTP remains accessible. Existing HTTP authorization and namespace-wide strict mutual TLS policies remain effective.
It removes its cluster afterward and uses a separate kubeconfig throughout.

== Operational tradeoffs

A server restart drops active playback and worker sessions.
Clients reconnect and workers establish a new session.
This single-server design avoids a shared worker database or message broker.

Segment bytes travel on separate bounded HTTP/2 streams over the worker channel.
Players continue to fetch playlists and segments from the server's HTTP endpoint.
See https://github.com/streamarr/streamarr-adr/blob/main/adr/0018-live-playback-authority-and-outbound-workers.adoc[ADR 0018] for the deferred multi-server boundary.
