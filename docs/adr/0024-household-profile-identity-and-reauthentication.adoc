= ADR 0024: Identity Separates Accounts, Households, Profiles, and Fresh Reauthentication

== Status

Accepted

== Context

Authentication establishes an Account, but playback and administration also depend on a Household and, for playback, a selected Profile.
Treating those concepts as one user object makes portable Profiles, Household roles, and restricted Profile safety difficult to express without copying authority into tokens.
Sensitive administration also needs proof that the Account recently repeated its authentication ceremony.

== Decision

An Account belongs to one Household and owns one personal Profile.
Profiles may be shared into other Households, and explicit manager relationships determine who may administer a Profile.
Household and ServerAdmin roles belong to Accounts; Profile restrictions never grant Account authority.

Access tokens use `ACCOUNT`, `PROFILE`, or `PLAYBACK` scope and carry the selected Profile and context Household needed to route a request.
These claims are signed snapshots, not live authority.
Login and refresh issue Account-scoped tokens until a valid Profile selection establishes Profile or Playback scope.
Refresh preserves remembered selection context but never preserves a fresh-reauthentication claim.

Sensitive mutations may require a recent password ceremony.
Reauthentication verifies the current Account synchronously and issues only a short-lived access token whose expiry is the earlier of the configured ceremony window and the source token expiry.
It does not issue or rotate a refresh token.
Browser reauthentication retains the existing session context and follows the normal access-cookie and CSRF contract.

Reads that would reveal whether an inaccessible Account, Household, or Profile exists use the same not-found outcome as an absent resource.
Database constraints enforce identity invariants that must remain true under concurrent writes, including the last enabled ServerAdmin and last HouseholdAdmin protections.

== Consequences

* Authentication, selection, playback, and administration can evolve without collapsing Accounts and Profiles into one authority object.
* Every authority-sensitive operation must consult live facts rather than trusting token role snapshots.
* Clients must handle an Account-scoped picker state and explicitly select a Profile before Profile or Playback operations.
* A fresh ceremony is deliberately lost on refresh, limiting replay of elevated access tokens.

== Rejected Alternatives

* Treating a Profile as the authenticated principal — Profiles are selectable personas and may be shared; they do not own credentials or Account authority.
* Treating token claims as current roles — revocation, disabling, and membership changes would remain effective only after token expiry.
* Rotating refresh credentials during reauthentication — it unnecessarily couples a short ceremony proof to long-lived session management.
