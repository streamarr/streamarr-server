= ADR 0021: Device Pairing Follows RFC 8628 Semantics over Streamarr Transport

== Status

Proposed

== Context

link:0016-authentication-mechanisms-and-session-security.adoc[ADR 0016] rejects lowering the bar for limited-input devices: a TV should not ask a person to type an account password on a remote control, and a password typed on the least-trusted screen in the house is the credential most likely to be shoulder-surfed or captured.
ADR 0016 records that such clients pair rather than authenticate.

This ADR settles how. The tvOS client displays a code; a person who is already signed in on the web confirms which device is asking and approves it; the TV polls and receives the ordinary bearer session every other client gets.

The load-bearing direction is *TV → person → web*. The TV asks the server for a code and shows it. The person carries it to a device where they are already authenticated. Nothing is typed into the TV, and the account password never reaches it.

== Decision

=== RFC 8628 semantics, Streamarr transport

The device-authorization grant's *semantics* are adopted wholesale: a device code the device polls with, a user code a person reads and types, an interval the server controls, and the four poll states `authorization_pending`, `slow_down`, `expired_token`, `access_denied`.

Its *transport* is not. Requests and responses are Streamarr JSON with camelCase fields, not RFC form-encoding, because every other endpoint in this server is JSON and one endpoint family speaking `application/x-www-form-urlencoded` would be a parser and a client-side special case for no benefit.
The RFC vocabulary rides the house error envelope as lowercase codes, on the poll endpoint only.

=== The two credentials are different things

The *device code* is a correlation handle the device polls with, **not** a credential a human types: 256 bits from `SecureRandom`, stored only as a SHA-256 digest, shape-validated before hashing so a malformed value is indistinguishable from an unknown one.

The *user code* is a display handle, **not** a secret: eight characters from RFC 8628's twenty-consonant alphabet, roughly 34.6 bits, stored as normalized plaintext because the web lookup has to find it. Its safety comes from being single-use, short-lived, and behind a guessing budget — never from entropy.

=== Every poll state is HTTP 400

Non-success poll outcomes are uniformly `400` with a lowercase code, **including `access_denied`** — never `401` or `403`.
A generic networking layer retries, refreshes, or logs out on `401`/`403`. Pairing states are not authentication failures, and a client whose HTTP layer cannot tell them apart would log a user out for the crime of not having approved yet.
`authorization_pending` is the normal answer to almost every poll, not an error.

=== The session is created at the winning poll

Approval marks the row `APPROVED` and records who decided it. No session, refresh token, or access token exists until a poll wins the row lock and consumes it.
Minting at approval would mean persisting a raw refresh token to wait for pickup, which is exactly the digest-at-rest property ADR 0016 is built on.

The poll/redeem path is **one row-locked transaction**, not a chain of conditional updates: with separate statements an approval committing between a claim and a cadence bump would classify a live `APPROVED` grant as expired. The lock is the same seam `RefreshTokenService.redeem` uses on the session row, and it serializes concurrent pollers so exactly one creates the session.

Expiry is a predicate over `expires_at`, never a stored status — an expired row needs no writer to become expired.

=== Approval authenticates a device, it does not choose a profile

Approval runs the existing `autoSelectContext`, so the TV receives whatever scope the account's shape implies and picks household and profile afterward through the existing selection endpoints (link:0015-authorization-profiles-and-content-controls.adoc[ADR 0015]).
An account with no memberships, or a household with no selectable profiles, is a *valid domain state* the client renders as guidance — not an authentication failure.

=== Issuance requires a canonical base URL

`verificationUri` is always absolute. A container knows only its internal address, so the server never invents one: without `STREAMARR_BASE_URL` it reports `devicePairingEnabled: false` and refuses issuance with `503`.
Only *new issuance* is gated — a code already shown to a person is always looked up, decided, polled, and redeemed to its normal terminal result, so a configuration change never strands a code mid-flow.

Production transport is HTTPS. `STREAMARR_ALLOW_INSECURE_HTTP` is honored only together with a development or test profile, because a single flag is one typo away from shipping cleartext credentials.

Contract endpoints never redirect: `/api/auth/**` and `/api/stream/**` return final responses, and deployments must not rewrite those paths, because clients reject 3xx on credential-bearing requests.

=== Three hard limits, on dimensions a proxy cannot collapse

`LoginThrottle` already learned the lesson: behind a reverse proxy every client shares one address, so a blocking per-source budget locks out everybody.

. *Issuance* — a global cap on outstanding `PENDING` rows, evaluated as a row count so it is DB-backed and cross-instance for free. `Retry-After` is the time until the oldest outstanding code expires, the moment capacity provably frees.
. *Polling* — the per-code `next_poll_at` gate, which is proxy-immune and cross-instance by construction.
. *Lookup and decision* — one shared account-keyed guessing budget. Lookup is the enumeration oracle (`200` with a device name versus `404`), so two separate budgets would hand an attacker twice the attempts.

=== Explicitly deferred

* Factor-gated approval (`FactorGrantedAuthority`) — ADR 0016 names device-pairing approval as the natural first target for step-up MFA; approval is `SCOPE_ACCOUNT` today.
* QR and deep-link accelerators, and with them `verificationUriComplete` — the field name is reserved and v1 servers do not emit it. No unconsumed protocol surface ships.
* DB-backed guessing budgets — single-JVM like `LoginThrottle`.
* Authenticated server identity, and any discovery TXT `id`.
* Email or magic-link pairing.

== Consequences

* A TV never handles an account password, and a stolen user code is worth nothing without a signed-in person who approves it.
* The approval surface is a dedicated `/link` page, so pairing is not user-complete until the web page ships; curl approval is a server smoke test.
* A lost pairing *success* response is not recoverable — no raw token is stored to re-deliver — so the TV requests a new code. Recovering it would mean persisting a raw token for re-delivery, which is the digest-at-rest property this design is built on.
* A won poll creates a session before its response reaches the TV; a lost response leaves that session with no holder until normal session reaping expires it.
* The outstanding-code cap is a shared resource: someone who can reach issuance can hold the cap and briefly starve legitimate pairing, bounded by the ten-minute TTL and the sweeper. Accepted for a self-hosted product, and preferred over proxy-fragile per-source blocking.

== Rejected Alternatives

* GraphQL mutations for pairing — link:0002-graphql-over-rest.adoc[ADR 0002] already excepts token issuance from the GraphQL-only rule, and pairing mints tokens exactly as login and refresh do. RFC 8628 states are HTTP-status and header shaped (`Retry-After`, per-state codes) where GraphQL has one 200 envelope; issuance and polling are pre-auth, so anonymous GraphQL would mean opening `/graphql` to unauthenticated traffic for four small endpoints; and a TV polls with a dumb HTTP loop before it has any GraphQL session. Splitting one pairing contract across two transports would be worse than four coherent REST endpoints.
* Typed credentials on the TV — ADR 0016 already rejected lowering the bar for limited-input devices.
* Spring Security's one-time-token login — heavier than a pending row plus a poll, and shaped for email delivery rather than a code read off a screen.
* Creating the session at approval — persists a raw refresh token waiting for pickup, breaking digest-at-rest.
* A full OAuth authorization server — Streamarr issues tokens to its own clients only; an AS dependency brings client registration, consent, and discovery surfaces nobody asked for.
* Digesting the user code — the web lookup must find a row by the code a person typed, which a digest forbids; single use, a short TTL, and the guessing budget carry its safety instead.
* A chain of conditional updates for poll/redeem — classification races (a live `APPROVED` grant reported expired) that the row lock removes outright.
* A `session_id` back-reference on the row — nothing reads it, and the sweeper deletes the row within minutes; `device_name` on `auth_session` is the durable audit record.
* `ON DELETE CASCADE` from the deciding account — would erase `CONSUMED` and `DENIED` decision history along with the account; `SET NULL` keeps the audit and the sweeper bounds the lifetime.
* A relative `verificationUri` fallback for zero-config pairing — clients would have to guess the origin, and the Apple client classifies a relative-URI server as incompatible. Cross-client determinism beat zero-config.
* Per-source alerting budgets — considered and cut: no client-visible behavior and four configuration properties for a signal nobody has asked for yet.
