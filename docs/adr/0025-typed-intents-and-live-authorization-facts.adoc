= ADR 0025: Authorization Uses Typed Intents and Live Facts at the Service Boundary

== Status

Accepted

== Context

GraphQL resolvers know transport details, while authorization rules protect application use cases and must remain correct for every current or future adapter.
Naming Cedar actions, building entity slices, or interpreting authority at call sites would spread policy-engine details across the codebase.
Role and session state can change while a signed access token remains valid, so token claims alone cannot make an authoritative decision.

== Decision

Adapters resolve the authenticated identity, translate protocol input and output, and pass identity explicitly to an application use case.
Authorization guarding a use case is enforced in the service layer.
Adapter-level authorization may be a fail-fast preflight, but it is never the authoritative or sole check.

Every point decision goes through `AuthorizationService.decide(identity, intent)` or `AuthorizationService.requireAllowed(identity, intent)` with a typed `Intent`.
`decide` supports resource operations whose expected denial becomes a typed payload outcome.
`requireAllowed` protects a whole surface and produces a top-level forbidden error.
Callers never name a Cedar action, assemble Cedar entities, or pass their own interpretation of authority.

Only `services.authorization.cedar` imports Cedar or its Java bindings.
The facade maps typed intents to package-private actions and obtains facts from focused contributors.
Authority-sensitive facts, including Account enabled state, session validity, Household roles, Profile relationships, and ServerAdmin status, are read live from PostgreSQL for the actions that require them.
The token ServerAdmin claim is routing and display data only, never authority.

Authorization failures fail closed as `AUTHORIZATION_UNAVAILABLE`.
Diagnostics are logged and metered but are never returned to clients.
A `ReauthenticationRequired` result is valid only when a fresh ceremony is the sole missing condition; a genuine authority denial remains denied.
ArchUnit confines engine dependencies, and JaCoCo holds the authorization module at 100 percent line and branch coverage.

== Consequences

* Authorization remains protocol-independent and cannot be bypassed by adding another adapter.
* Policies can change engines without changing service signatures or exposing Cedar concepts outside the module.
* Decisions perform the live reads needed to observe revocation and role changes immediately.
* Typed denial and infrastructure failure remain distinguishable without leaking policy diagnostics.

== Rejected Alternatives

* Authorizing only in GraphQL resolvers — non-GraphQL callers could bypass the protected use case.
* Passing Cedar actions or entity maps from callers — policy-engine structure would become part of the application API.
* Trusting signed role claims until expiry — disabled Accounts and revoked authority would retain access.
