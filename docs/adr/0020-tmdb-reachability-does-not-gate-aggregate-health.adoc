= ADR 0020: TMDB Reachability Does Not Gate Aggregate Health

== Status

Accepted

== Context

`GET /actuator/health` was reported hung in a container deployment: it returned zero bytes in 45 seconds.
During the same incident, `/actuator/health/liveness`, `/actuator/health/readiness` and `/api/auth/status` all answered in milliseconds.
Only the aggregate stalled because the liveness and readiness groups exclude custom contributors such as TMDB.
`TmdbHealthIndicator` used the metadata-enrichment HTTP client, whose connection, retry and rate-limit budgets are appropriate for library work but not for a health endpoint.
A per-request timeout bounds one HTTP exchange, not time spent in Methanol interceptor queues or retry backoff.
A `429` can trigger up to five retries, honoring `Retry-After` when present or using the configured 2s..32s fallback.
A saturated library scan can also queue the probe behind enrichment on the shared rate limiter.

The design also created two operational problems.
A live third-party call on every hit is an amplifier: an uptime monitor polling every 10 seconds becomes six TMDB requests a minute, forever.
An unreachable TMDB also made `/actuator/health` report `DOWN`, so a container healthcheck targeting that endpoint could restart a server that was still serving playback, auth and browsing.

Spring Boot offers no property to keep a contributor out of the root aggregate.
`AutoConfiguredHealthEndpointGroups` builds the primary group with `HealthContributorMembership.always()`; `include`/`exclude` exist only for named groups.

== Decision

The TMDB health probe is bounded and cached, and its verdict is an enrichment signal rather than a traffic-admission signal.

* The probe uses a dedicated `tmdbHealth` Methanol client with no cache, retry interceptor or rate-limit interceptor. It appends `/configuration` to the enrichment client's `tmdb.api.base-url`. `tmdb.health.probe-timeout` (2s by default) applies to connection establishment, the client-level request timeout and the explicit request timeout. The enrichment client keeps its longer budgets and interceptors.
* The verdict is held for `tmdb.health.cache-ttl` (30s by default, one day maximum) in an `AtomicReference`. Expiry starts after the probe completes, and interruption-derived verdicts are not cached.
* Cache misses are deliberately unsynchronized, so simultaneous misses may probe in parallel. Cache publication uses `compareAndSet` against the snapshot that triggered the probe. The first completed probe wins, and an older delayed result cannot overwrite it. This avoids holding coordination across external I/O.
* A `200` or unauthenticated `401` proves reachability. Network failures and other HTTP responses produce `DEGRADED`, never `DOWN`, because TMDB availability affects metadata enrichment rather than traffic admission.
* `DEGRADED` uses the neutral description "TMDB metadata service is unavailable" across those failure paths. Unexpected HTTP statuses are logged with their numeric code.
* `management.endpoint.health.status.order` ranks `DEGRADED` below `UP`, so the status cannot pull the aggregate down.
* `/actuator/health/metadata` is where TMDB reachability stays observable and alertable, mapping `DEGRADED` to 503 so a monitor pointed at it still fires.

Explicitly deferred:

* The `ffmpeg` contributor still gates the aggregate; whether a missing transcoder means "do not send traffic here" is a separate decision.

== Consequences

* A TMDB outage no longer restarts healthy servers. TMDB's contribution completes within the probe budget instead of retrying or queueing behind enrichment.
* The root status is not a reliable TMDB alert; operators must monitor `/actuator/health/metadata` instead.
* A custom status code exists in the health vocabulary, so anything parsing health JSON must tolerate `DEGRADED`.
* The probe no longer exercises enrichment's retry, rate-limit or HTTP-cache path. It still uses Methanol with the platform's proxy and TLS defaults.

== Rejected Alternatives

* Removing the indicator, or not registering it as a bean — the aggregate stops lying, but operators lose the only signal that enrichment is degraded.
* Sharing the enrichment client and relying on the request timeout — the timeout governs an individual HTTP exchange, not retry backoff or rate-limit queueing, so the endpoint can still exceed its budget and health probes compete with metadata traffic.
* Wrapping the shared client with `sendAsync(...).get(timeout)` — this bounds the Actuator caller's wait, but cancellation propagation through the interceptor chain is not a structural guarantee. An abandoned retry or rate-limited operation may continue consuming resources and competing with enrichment after the health response returns.
* Registering the contributor into a group only — not expressible: the primary group's membership is `always()`, and there is no root `exclude`.
* A custom `StatusAggregator` bean — it receives a set of statuses, not which contributor produced them, so it cannot single out TMDB, and it would apply to every group.
* A `HealthEndpointGroupsPostProcessor` that wraps the primary group to drop the member — hand-rolled machinery to express what a status rank already expresses in configuration.
* Reporting `UNKNOWN` instead of a custom status — it is already ranked below `UP`, but it reads as "could not determine" when we determined that TMDB metadata is unavailable.
* Relying on the aggregator ignoring statuses absent from the order list — true of `SimpleStatusAggregator` today, but undocumented; an explicit rank below `UP` survives a later reader who edits the order property.
* Leaving the aggregate `DOWN` and pointing container healthchecks at `/actuator/health/readiness` — the aggregate would still misreport, and every operator would have to learn the workaround.
