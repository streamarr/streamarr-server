= GraphQL Subscriptions

Streamarr delivers live changes over GraphQL subscriptions.
Every client with a selected Profile receives library status, additions and removals.
Every client of a Profile receives that Profile's watch-state changes.
Every signed-in client receives the changes to the Profile shares it may read.
https://github.com/streamarr/streamarr-adr/blob/main/adr/0042-graphql-subscriptions-run-over-websocket-until-token-expiry.adoc[ADR 0042] records the decision.
The schema descriptions in `src/main/resources/schema/root-subscription.graphqls` define each field, and `profile-sharing.graphqls` defines `profileShareChanged`.

== Transport

Subscriptions run only over the `graphql-transport-ws` WebSocket protocol on `/graphql`.
Queries and mutations run only over HTTP `POST /graphql`.

The server refuses an operation on the wrong transport before it executes:

* A subscription sent over HTTP gets the error code `WEBSOCKET_REQUIRED`.
* A request that asks for `text/event-stream` gets HTTP 406 and the error code `WEBSOCKET_REQUIRED`.
* A query or mutation sent over the WebSocket gets the error code `HTTP_REQUIRED`.

== Authentication

The opening HTTP handshake carries the credential.
Browsers send the access cookie.
Native clients send an `Authorization: Bearer` header.
The `connection_init` payload carries no credential.

The handshake answers:

[cols="1,3"]
|===
|Response |Meaning

|101
|The socket is open. Send `connection_init` next.

|401
|No credential, or the access token is invalid or expired. Refresh the token, then reconnect.

|403
|The `Origin` header names another site.
|===

A browser may connect from the server's own origin or from the origin of `STREAMARR_BASE_URL`.
A request without an `Origin` header, as native clients send, passes the origin check.
Browsers report every refused handshake as close code 1006 and hide the HTTP status.
A browser client that sees 1006 before `connection_ack` refreshes its token before it reconnects.

Each operation is authorized when the client subscribes.
A refused caller gets a `next` message with an error code, then `complete`.
`libraryStatusChanged` refuses a caller who is not a ServerAdmin with `FORBIDDEN`.
`profileShareChanged` needs no selected Profile.
It refuses a device-bound session and a disabled Account with `FORBIDDEN`, and it decides again for each change, as <<Profile shares>> describes.
Every other field refuses a token without a selected Profile with `PROFILE_REQUIRED`.
It refuses a caller without the ViewProfileActivity permission for that Profile with `FORBIDDEN`.
`AUTHORIZATION_UNAVAILABLE` means the server could not decide; retry later.

== Access token expiry

A socket lives no longer than the access token that opened it.
At expiry the server closes the socket with code 4100 and the reason `Access token expired`.
The server sends no `complete` message first.
The client refreshes its token, opens a new socket, and subscribes again.

== Slow clients

The server holds at most `GRAPHQL_SUBSCRIPTION_CONNECTION_SEND_BUFFER` unsent bytes for each socket.
A client that stops reading lets those bytes grow.
When one more frame would exceed the limit, the server discards the unsent frames, ignores further messages, and closes the socket with code 4101 and the reason `Client fell behind`.
One frame larger than the limit closes the socket the same way.
The client reconnects, subscribes, and runs its queries again.
Other sockets keep receiving changes, and scans and refreshes continue.

== Close codes

[cols="1,3"]
|===
|Code |Meaning

|4100
|The opening access token expired. Refresh, reconnect, and subscribe again.

|4101
|The client fell behind. Reconnect, subscribe, and query again.

|4400
|The client sent a message the protocol does not allow.

|4401
|The client subscribed before `connection_ack`.

|4408
|The client sent no `connection_init` within `GRAPHQL_WEBSOCKET_CONNECTION_INIT_TIMEOUT`.

|4409
|The client reused the id of a running operation.

|4429
|The client sent a second `connection_init`.

|1001
|The server is shutting down. Reconnect.

|1011
|The server failed unexpectedly. Reconnect after a delay.
|===

The codes 4400, 4401, 4409 and 4429 report a client defect.
A client stops and reports these codes instead of reconnecting.

== Operation errors

[cols="1,3"]
|===
|Code |Meaning

|`PROFILE_REQUIRED`
|The field needs a selected Profile, and the access token has none. The operation ends.

|`FORBIDDEN`
|The caller may not subscribe to the field. The operation ends. A `profileShareChanged` operation can also end this way at a later change, in an `error` message.

|`AUTHORIZATION_UNAVAILABLE`
|The server could not decide authorization. Subscribe again later.

|`SUBSCRIPTION_OVERFLOW`
|Changes for the operation arrived faster than the server could resolve them, and more than `GRAPHQL_SUBSCRIPTION_OPERATION_BUFFER` waited. The server ends that operation with an `error` message. Subscribe again, then run the field's queries again. A client that stops reading gets close code 4101 instead.

|`TOO_MANY_OPERATIONS`
|The connection already runs `GRAPHQL_SUBSCRIPTION_MAX_OPERATIONS_PER_CONNECTION` operations. Complete one first.
|===

A subscription never completes normally while the server runs.
Another unexpected failure ends the operation with the error `Subscription error`.

== Field errors

A field error does not end the operation.
When a selected field of one change fails to resolve, the server still sends the change in a `next` message.
The failed field arrives as `null`, and the message's `errors` name the path of each failed field.
Later changes keep arriving on the same operation.

A failed non-null field passes its `null` up to the nearest nullable parent.
A failed non-null field of a delivered library or removal makes the whole change `null`.
A failed non-null field of a watch-state item makes only that item `null`, as <<Failed changes>> describes.
Every subscription root field is nullable, and `items` holds nullable elements, so a `null` stops at the item or at the subscription field.
graphql-java ends a subscription when a `null` reaches a non-null root field, so a non-null root would turn one failing field into a terminal `error` message.

A client keeps the operation running through these messages:

* A web client that uses Apollo Client sets `errorPolicy: 'all'` on each subscription, so the client receives the data together with its errors.
* The client applies the rest of the change.
It skips a `null` subscription field and each `null` item, and keeps its previous value for each field that an error names.

A later change may not repeat a value that failed, so the client's state can stay stale until that value changes again.
After a message that carries `errors`, the client runs its queries again through the same recovery path it uses after a reconnect.
A library status client queries `libraries` again.
A watch-state client runs the queries from <<Building current state>> again.
The subscription stays open while those queries run.

== Client lifecycle

A Library list client subscribes to `libraryAdded` and `libraryRemoved` first and then queries `libraries { id name }`.
A ServerAdmin client that also shows status subscribes to `libraryStatusChanged` and queries `libraries { id name administration { status scanStartedOn scanCompletedOn } }`.
It applies each change by library id.
The server sends no snapshot and replays nothing missed.
After every reconnect, the client subscribes and queries again.

Each field delivers one library's changes in commit order.
There is no order across libraries or across fields: `libraryAdded` and `libraryStatusChanged` for one library may arrive in either order.
A client that receives `libraryStatusChanged` for a library it does not hold yet adds that library.
`libraryStatusChanged` delivers the library as the server reads it after the change.
A client may miss an intermediate status, but the last change it receives carries the latest status.

Clients reconnect with an exponential, jittered delay capped near 30 seconds, and retry without limit.
They stop on logout, on a permanent authentication failure, and when the client is disposed.
Before each reconnect after 4100 or a refused handshake, the client refreshes its token.

* Web clients use the `graphql-ws` library.
Its default retry wait grows without a cap, and it stops after five attempts, so the client sets `retryAttempts: Infinity` and a capped `retryWait`.
`graphql-ws` retries 1001, 1006, 4100, 4101 and 4408 itself.
It treats 1011, 4400, 4401, 4409 and 4429 as fatal, so the client reconnects after 1011 itself.
* Apple clients use the Apollo iOS WebSocket transport.
It reports no close code: any server close ends the subscription stream.
It does not reconnect by default, and when enabled it reconnects once after a fixed interval.
The app reconnects with its own backoff and passes the fresh token through `updateHeaderValues(_:reconnectIfConnected:)`.

A client closes its socket on logout and when the user switches Profile or Household, because the socket keeps the authority it opened with.
It discards changes that arrive from the old socket after the switch, so they never reach the new identity's cache.

== Watch state

`watchStateChanged` delivers the selected Profile's committed watch-state changes.
The Profile comes from the access token that opened the socket.
No argument names the Profile.

=== Building current state

A client subscribes first and then runs its ordinary queries: `continueWatching`, the library views it shows, and any detail views.
It selects the same fields in the subscription as in those queries.
The server sends no snapshot and replays nothing missed.
After every reconnect, the client subscribes and queries again.

=== What a change holds

Each committed write sends one change.
A change lists each movie or episode whose watch state changed, and a client selects that watch state through each item's `selectedProfileState { watchState { ... } }`.
It also lists the season and the series of each such episode, because their aggregate values may have changed.
Each item appears once in a change.
The server reads the values when it delivers the change, so they are current values, not differences.
A client applies a change by item id, and applying a change twice changes nothing.
An item removed after the write is left out of the change.

Marking a series watched lists every episode of the series.
A client keeps its subscription fragments lean, because a large selection can exceed `GRAPHQL_SUBSCRIPTION_CONNECTION_SEND_BUFFER` and close the socket with 4101.

=== Who receives a change

Every open socket of the Profile receives the change, including the socket of the client that made the write.
No socket of another Profile receives the change, even in the same Household.
A socket keeps the Profile of the token that opened it.
After a Profile or Household switch, the client closes the old socket and discards its changes, as described in <<Client lifecycle>>.

=== Order

The server delivers one operation's changes in order, one at a time.
The last change an operation receives carries the latest values.
An intermediate change may already carry values from a later write.
There is no order across operations or across fields.

=== Keeping lists current

A client keeps its lists current with the same rules the server's queries use.
It needs no follow-up query.

* *Continue Watching* queries `continueWatching(first, after) { edges { cursor orderKey node { ... } } pageInfo { ... } }`.
The existing watch-state subscription carries `items` for independent entity updates and `continueWatching { itemId edge { cursor orderKey node { ... } } }` for list changes.
The change list includes every touched movie or episode, including departures with a null edge.
A null change list means membership is unknown: preserve the shelf and still apply usable `items`.
Continuation work is bounded by the selected Profile: the query groups that Profile's progress before applying the cursor, so it does not promise an index seek directly to the next shelf page.
The connection and event edges share counted-resume-position membership and last-watched ordering, including the descending ID tie-breaker.
Clients select full card fields on event nodes, merge eligible edges by ID, compare opaque `orderKey` values as ascending ASCII strings, and retain at most their shelf cap.
An explicitly null edge with no error affecting that change's response path removes the item without reading a replacement; membership is independent of the cap.
A non-null edge with a null node never removes an item. Error paths include aliases and list indices; preserve affected changes and recover through the shared subscription lifecycle.
An existing eligible item moved to the tail remains while it fits the cap; an initially full shelf does not establish a permanent boundary.
`pageInfo.hasNextPage` describes query-time coverage and does not change this policy or promise an exact live top-N shelf.
Compare keys only within this Profile's Continue Watching list.
This is the bounded shelf policy in https://github.com/streamarr/streamarr-adr/blob/main/adr/0046-home-continue-watching-keeps-a-cap-without-backfill-reads.adoc[ADR 0046].
* *Library views* use `edge(sort, filter)` from `libraryItemAdded` and `libraryItemUpdated`, with the same arguments as `Library.items`.
The server supplies the same `MediaEdge` as the query, including an opaque `orderKey` and usable cursor, for watch-status filters and `LAST_WATCHED` ordering too.
The independent `item` selection updates entity data even when the edge is null because the item left a filtered view.
Clients compare keys against their loaded window and reconcile by item ID; they do not reconstruct filter or sort rules from selected entity fields.
See link:library-contents.md[Live library contents] for window boundaries, removals and recovery.

A client keeps the `pageInfo` cursors from its last page query and never builds a cursor.
A cursor stays a valid position after its item leaves the view or moves.
When the client loads the next page, it drops items it already holds by id, because a moved item can arrive twice.

=== Failed changes

The server resolves each change for each subscriber.
A field that waits on a batched load, such as `watchStatus` under `selectedProfileState`, fails when it cannot resolve within `GRAPHQL_SUBSCRIPTION_DELIVERY_FETCH_TIMEOUT`, so later changes do not wait behind it.
The timeout does not bound `items`, which reads the database directly.
A stalled read of `items` holds back the operation's later changes until the read completes.
Every database statement that waits on a lock fails after `DATABASE_LOCK_TIMEOUT`, `30s` by default, so a read held back by a lock ends within that bound.
PostgreSQL ends a database session whose transaction issues no statement for `DATABASE_IDLE_IN_TRANSACTION_TIMEOUT`, `60s` by default, and releases the locks that transaction held.
A failed nullable field, such as `watchProgress` or `lastWatchedAt`, arrives as null in a `next` message.
A failed non-null field under `selectedProfileState`, such as `watchStatus`, makes `selectedProfileState` null, and the item keeps its other fields.
A failed non-null field of the item itself, such as `library` or `unmatched`, makes that item null in `items`.
The other items of the change arrive intact.
When the change's items cannot be resolved, `watchStateChanged` arrives as null.
The operation continues in every case, and the client recovers as <<Field errors>> describes.

== Profile shares

`profileShareChanged` delivers each committed change to a Profile share.
A change arrives when a share is offered, accepted, declined, canceled, invalidated or ended, when an offer expires, when a share starts or stops being required by Account membership, and when a share is deleted with its Profile or its Household.
When a Profile moves to another Household, a change also arrives for each of its shares into the Household it leaves and the one it joins, because whether it is a visitor there changes.
A change that rolls back never arrives.
Each change carries `shareId` and `share`, the share as the server reads it when it delivers the change.

=== Who may subscribe

Any signed-in session may subscribe, with or without a selected Profile.
A device-bound session gets `FORBIDDEN`, and so does a disabled Account.

=== Who receives a change

The server decides each change as it delivers it, with the same reads as the share queries:

* The target Household's HouseholdAdmins and ServerAdmins, who read the share through `householdShares`.
* The Profile's managers and ServerAdmins, who read it through `profileShares`.

The Account of a self-managed Personal Profile is one of its managers.
The Account of a supervised Personal Profile, such as a Kid's, is not: it receives no change of that Profile's shares.
A HouseholdAdmin who only hosts a Profile receives that Profile's share into their own Household and no other.
The share's fields are hidden from the same readers as in the queries.
A subscriber who stops managing a Profile stops receiving its changes at once.
An Account that is disabled after subscribing gets an `error` message with `FORBIDDEN` at the next change, and the operation ends.
The HouseholdAdmin role comes from the access token, so a HouseholdAdmin who loses that role keeps receiving their Household's changes until the token expires, as with the queries.

=== The last change a Household receives

The target Household's HouseholdAdmins follow a share while the offer is `PENDING` or the share is `ACTIVE`.
They also receive the change that ends it: the offer is declined, canceled, expired or invalidated, or the share ends.
That last change carries the share's own fields, such as `status`.
Its `profile`, `visitor`, `offeredByDisplayName`, `household` and `invalidationReason` are `null`, as in the queries, which no longer list the share for them.
The client takes the share out of its lists when that change arrives.
No later change of the share reaches them, not even its removal, and the share mutations answer `ShareNotFoundError` for it, as for a share that no longer exists.
ServerAdmins and the Profile's managers receive every change of the share.

=== Removals

A change whose `share` is `null`, with no `errors`, removes the share: it was deleted with its Profile or its Household.
A share deleted with its Profile reaches those who may read its Household's shares: its HouseholdAdmins only while it is pending or active, and ServerAdmins always.
A share deleted with its Household reaches those who may read its Profile's shares.
A `null` share with `errors` is not a removal: the client keeps the share and runs its queries again.
A share that stops being readable to the subscriber does not arrive as removed; the queries stop listing it.

=== Expiry

An offer whose time runs out reads as `EXPIRED` in the queries at once.
The server stores `EXPIRED` on such offers every `AUTH_SHARING_EXPIRY_SWEEP_INTERVAL`, `1m` by default, and each one then arrives as a change.

=== Building current state

A client subscribes first and then queries `householdShares` or `profileShares`.
It applies each change by `shareId`, and keeps a share in a list while its status is one of the list's statuses.
In a `householdShares` list kept to `visitorsOnly`, it also keeps a share only while its `visitor` field is true.
The lists put the newest share first, so a share created after the client subscribed goes first.
The server delivers one operation's changes in order, so the last change for a share carries its latest state.
After every reconnect, the client subscribes and queries again.

== Configuration

[cols="2,1,3"]
|===
|Variable |Default |Meaning

|`GRAPHQL_WEBSOCKET_CONNECTION_INIT_TIMEOUT`
|`10s`
|How long the server waits for `connection_init`.

|`GRAPHQL_WEBSOCKET_KEEP_ALIVE`
|`20s`
|How often the server sends `ping`. Keep it below the proxy idle timeout.

|`GRAPHQL_SUBSCRIPTION_OPERATION_BUFFER`
|`64`
|How many changes may wait for one operation before `SUBSCRIPTION_OVERFLOW`.

|`GRAPHQL_SUBSCRIPTION_MAX_OPERATIONS_PER_CONNECTION`
|`32`
|How many operations one socket may run at once.

|`GRAPHQL_SUBSCRIPTION_CONNECTION_SEND_BUFFER`
|`1MB`
|How many unsent bytes one socket may hold before it closes with 4101.

|`GRAPHQL_SUBSCRIPTION_DELIVERY_FETCH_TIMEOUT`
|`10s`
|How long one asynchronous field of a delivered change may take to resolve. A slower field fails.
|===

The server refuses to start when a subscription limit or the delivery fetch timeout is missing, zero, or negative.
Tomcat ends a socket write that stalls for 20 seconds.

== Reverse proxies

A reverse proxy in front of the server must pass WebSocket upgrades on `/graphql`:

* Forward the `Upgrade` and `Connection` headers.
* Set the read timeout above `GRAPHQL_WEBSOCKET_KEEP_ALIVE`.
* Set `STREAMARR_BASE_URL` to the public URL, or forward `Host` and `X-Forwarded-Proto` and set `SERVER_FORWARD_HEADERS_STRATEGY=native`.

Without the last step, browsers send a public `Origin` that the server rejects with 403.
