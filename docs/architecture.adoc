= Architecture Overview

== Tech Stack

* **Java** (LTS), **Spring Boot**, **PostgreSQL**
* **GraphQL** via Netflix DGS
* **jOOQ** for complex queries (keyset pagination)
* **Flyway** for database migrations
* **FFmpeg** for HLS transcoding and remuxing runs only in standalone transcode workers (https://github.com/streamarr/streamarr-transcode-worker[streamarr-transcode-worker]); the server executes no media processes

== Dependency Boundaries

----
Protocol adapters ---> Services ---> Repository contracts
                          |                 ^
                          v                 |
                     Domain model <--- Repository implementations ---> PostgreSQL
----

Arrows point from consumers to their dependencies.
Repository implementations fulfill the contracts used by services.
Services, repository contracts, and repository implementations share domain types.

* *Protocol adapters* (GraphQL resolvers, REST controllers) delegate to services -- no business logic at the protocol layer
* *Services* orchestrate business operations -- protocol-agnostic (no `graphql.*` imports, enforced by ArchUnit)
* *Repository contracts* expose data access and atomic operations needed by services
* *Repository implementations* use JPA for CRUD and jOOQ for complex queries
* *Domain* defines the core model and does not depend on services, repositories, or protocol adapters

These rules are enforced by ArchUnit tests (see https://github.com/streamarr/streamarr-adr/blob/main/adr/0014-protocol-agnostic-pagination.adoc[ADR 0014] for pagination-specific architecture).

PostgreSQL-specific coordination belongs in repository implementations.
`PostgresTransactionLocks` shares advisory-lock and transaction-local timeout operations within persistence.
Services request atomic operations through repository contracts; lock keys and PostgreSQL calls stay inside the implementations.
See https://github.com/streamarr/streamarr-adr/blob/main/adr/0031-transaction-scoped-artwork-replacement-locking.adoc[ADR 0031] for the artwork replacement protocol.

== Database

PostgreSQL with UUID primary keys, custom ENUMs, and audit columns (`created_on`, `modified_on`, `created_by`, `modified_by`) on all entities.

Entity hierarchy uses JPA JOINED inheritance:

----
BaseAuditableEntity (UUID primary key, audit columns)
    └── BaseCollectable (title, summary, release_date)
            ├── Movie
            └── Series
----

== GraphQL API

Netflix DGS with Relay-style cursor-based pagination:

* `MediaConnection` / `MediaEdge` / `PageInfo`
* Keyset (seek) pagination via jOOQ for performant infinite scroll
* Subscriptions over the `graphql-transport-ws` WebSocket on `/graphql` for live library status, library contents and watch-state changes; queries and mutations stay on HTTP. See link:graphql-subscriptions.adoc[GraphQL Subscriptions].

== Metadata Pipeline

----
Library Scan
    → Walk filesystem
    → Parse filename (regex-based, 59+ test cases)
    → Search TMDB for match
    → Enrich with TMDB metadata (cast, studios, ratings)
    → Persist Movie + MediaFile + relationships
----

The metadata provider abstraction (`MetadataProvider<T>`) allows swapping TMDB for another source without changing the scan pipeline.

=== Admission

A scan admits one task per media file, and a refresh admits one task per series or movie (https://github.com/streamarr/streamarr-adr/blob/main/adr/0041-scans-and-refreshes-admit-tasks-through-an-adaptive-limit.adoc[ADR 0041]).
An adaptive concurrency limit decides how many tasks run at once.
The limit uses Netflix concurrency-limits' Gradient2 algorithm: it rises while task latency holds steady and falls when latency rises.
The connection pool is not a queue for library work.

The thread that walks the library acquires an admission before it pulls the next file, so the walk never runs ahead of admission.
Ignored files and files without a supported video extension take no admission, and neither does a title without a TMDB id.
Each admitted task forks on a virtual thread that runs as the System actor, and the tasks join in the order they were admitted.

Each admitted task reports exactly one outcome, which returns its admission:

* A task that called the metadata provider reports its latency.
* A task that returned without real processing reports that it was ignored. This covers a file that was already matched, a file whose name could not be parsed, a misconfigured provider, an interrupted task, and a task that threw without a timeout cause. Ignored reports do not move the limit.
* A task that hit a TMDB retry, recorded a temporary failure, threw because of a timeout, or could not read its artwork results reports a drop. Gradient2 reads a drop as an ordinary latency sample.

A task keeps its admission until the primary artwork it requested has recorded results, so its latency includes that artwork.
A series file task waits for every series, season and episode image it requested.
The task checks its results every `artwork.runs.task-result-check-interval` (100 ms by default), and a task that requested no artwork reads nothing.
A failed read stops that task's wait, and the operation reads the same results again when it waits for its artwork at its end.

A recorded failure does not fail the operation.
A task that throws ends admission: the admitted tasks finish, files or titles that were not admitted yet are not processed in that operation, and the operation fails.
One task's failure never cancels another task.

Each scan and refresh starts with a fresh limit.
The tuning lives in `AdaptiveAdmission.learnedLimit()`: initial limit 16, minimum 1, maximum 200, queue size 1 and RTT tolerance 1.0.
Ignored reports never move the limit, so an unchanged rescan, whose tasks all report ignored, runs at most 16 tasks at once for the whole scan.

The limit applies when a task is admitted.
When Gradient2 lowers the limit, the tasks already admitted keep running, so `in_flight` can read above `limit` until enough of them report.

Admission publishes these metrics:

[cols="2,1,3"]
|===
|Metric |Tags |Meaning

|`streamarr.library.admission.limit`
|`operation`, `library`
|The current limit of a running scan or refresh. The gauge is removed when the operation ends.

|`streamarr.library.admission.in_flight`
|`operation`, `library`
|Admissions held: admitted tasks that have not reported yet, plus the admission the walking thread holds while it pulls the next subject. The gauge is removed when the operation ends.

|`streamarr.library.admission.admitted`
|`operation`
|Tasks admitted.

|`streamarr.library.admission.reports`
|`operation`, `report`
|Reports by kind: `latency`, `ignored` or `drop`.
|===

=== Item Failures

A scan or refresh finishes even when individual items fail, and the database keeps why each one failed.
Item failures never change the library's status.

[cols="1,2,2"]
|===
|Step |Where the result lives |Retried by

|Matching a media file
|`media_file.status`; `METADATA_UNAVAILABLE` and `ENRICHMENT_FAILED` also store `failure_reason`
|The next scan, which rematches every file that is not `MATCHED`

|Movie and series metadata refresh
|`item_result` with step `METADATA`
|The next refresh

|Artwork
|`item_result` with step `ARTWORK`, one row per image type, with the attempted source key and the generation of the artwork request it answers
|The item's artwork steps, a db-scheduler task, with backoff capped at five minutes, until every image has a final result

|Probe
|Terminal errors in `media_file_container_info.probe_error` with the source snapshot and probe version; the reason of the latest failed attempt at the requested inputs in `media_file_probe_task_request`
|db-scheduler, with backoff capped at five minutes, for failed attempts

|Keyframe packet scan
|`media_file_container_info.keyframe_status` and `media_file_keyframe_positions` on the outcome that asked for the scan; `PACKET_SCAN_FAILED` after three scans that timed out or reported no keyframes; other failures in the `media-file-keyframe-scan` task in `keyframe_scan_scheduled_tasks`
|A db-scheduler of its own, with backoff capped at five minutes; the next library scan requests a scan that the outcome still needs
|===

An `item_result` row holds the latest attempt's outcome: `SUCCEEDED`, `UNAVAILABLE` when the provider has nothing, or `FAILED` with a reason.
The reasons are `DOWNLOAD_FAILED`, `INVALID_MEDIA`, `TEMPORARY`, and `MISCONFIGURED` (a missing provider or rejected provider credentials).
A probe attempt records `SOURCE_INACCESSIBLE` when the worker or the server cannot read the source, `MISCONFIGURED` when no connected worker supports the source namespace or probe version, and `TEMPORARY` otherwise.
A probe that waits for a busy worker, or whose attempt was cancelled, records nothing and stays pending.
An artwork step records a saved image, or a stored image that the refresh mode keeps, as `SUCCEEDED`, an image type the provider does not offer as `UNAVAILABLE`, and a failed image as `FAILED`.
A network error, a `5xx`, `408` or `429` answer, and a storage or lock timeout are `TEMPORARY`; other `4xx` answers are `DOWNLOAD_FAILED`, and an undecodable image is `INVALID_MEDIA`.
A run that keeps every stored image of an item requests nothing for it and counts those images as skipped.

Each row stores when its attempt started.
A failure or unavailable result never replaces a result from a later attempt, so a stale failure cannot overwrite a successful retry.
Within one artwork generation, a failure never replaces a saved image's result either, so an overlapping attempt that fails cannot mark a saved image as failed.
A saved image's result is written in the same transaction as the image, so it always describes the stored artwork; concurrent replacements still follow the last-committer-wins rule in https://github.com/streamarr/streamarr-adr/blob/main/adr/0031-transaction-scoped-artwork-replacement-locking.adoc[ADR 0031].
An artwork step's failed, unavailable, and kept results are written together in one transaction, so a failed write leaves all of them pending rather than some written and some lost.
Matching failures are written only while the file is not `MATCHED`.
A failed image replacement keeps the existing image.
When a matching or metadata result cannot be written, the database error reaches the caller: matching fails the scan, and a refresh fails.
When an artwork result cannot be written, the step stays pending and its scheduled task retries it; a scan or refresh that waits for the image waits for the retried result.
A saved image whose result cannot be written rolls back with it, its files are deleted, and the attempt records a `TEMPORARY` failure instead.

A terminal probe error is reused while the source snapshot and probe version are unchanged; scans and refreshes do not force a new probe for it.

=== Artwork Steps

The transaction that records an item's metadata also stores its artwork request in `artwork_request` and schedules the item's artwork steps, so a committed request is never lost before its steps run.
Each item has at most one request, with its sources and refresh mode.
A request with changed sources or a stronger refresh mode replaces a pending one under a new generation and keeps the stronger mode; an identical request changes nothing.

Movie, series, season, and episode artwork is primary artwork; person and company artwork is background artwork.
Each priority runs on its own db-scheduler with its own table (`primary_artwork_scheduled_tasks`, `background_artwork_scheduled_tasks`) and thread cap (`artwork.scheduling.primary-threads`, `artwork.scheduling.background-threads`), so a backlog of background artwork never takes the threads of primary artwork, and neither takes the threads that run probes.
Image decoding, resizing, and BlurHash encoding hold one of a bounded set of CPU permits (`cpu.permits`); a freed permit goes to primary work first.

An attempt runs the steps of the request's current generation that have no final result yet, so repeating an attempt is safe.
A step saves images and records results only while its generation is still the item's pending request: it locks the item row and then the request row of that generation first.
An attempt that a newer request or a deletion made obsolete saves nothing, records nothing, and deletes the files it wrote.
The scheduled task is removed only together with the request of the attempted generation; a newer generation runs at once.
A step left to retry waits for the longer of the image host's `Retry-After` and the capped exponential backoff.
Saving a request, completing a scheduled task, and saving an attempt's results wait at most `artwork.request-lock.timeout` for the item's request lock and request row; saving images waits at most `image.replacement-lock-timeout`.
A step whose save times out stays pending and its task retries it; a metadata transaction whose request save times out fails.
A restart resumes pending steps, and db-scheduler revives the execution of a crashed server as a dead execution.

A scan or refresh waits for primary artwork by reading recorded results, never an in-process signal, so a result recorded after a restart counts.
A wait is satisfied only by a result of the awaited generation or a newer one; a failed result counts, and its retry continues in the background.
Server-wide progress reads stored state, so it is correct across restarts.
It counts as pending each requested image without a final result of its request's generation.
Its busy period starts when the earliest pending request was first made; a changed request keeps its first request time.
It counts the results recorded since the busy period started.

=== Deleting Items

`item_result`, `image`, and `artwork_request` rows reference their movie, series, season, episode, person, or company through generated columns with `ON DELETE CASCADE` foreign keys.
Every delete path therefore removes an item's results and image rows, and the database rejects a result or image for an item that does not exist.
A delete locks its items, including a series' seasons and episodes, before it reads their artwork paths, and it deletes those files only after it commits; a rolled-back delete keeps every file.

Writers of results and images lock the item row with `FOR KEY SHARE` before any result or image row.
Artwork steps then lock the item's artwork request row of their generation with `FOR SHARE`, so the full order for a replacement is advisory lock, item row, artwork request row, image rows.
A delete then waits for a writer holding the item and removes what it wrote, or finishes first and leaves the writer nothing to write for.
A guarded result for a deleted item records nothing, as a stale attempt does; an artwork step for a deleted item saves nothing and deletes the files it wrote.

== Service Communication

Services coordinate library lifecycle events using Spring Application Events rather than direct method calls. `LibraryManagementService` publishes events; interested services listen and react independently.

----
addLibrary()
    → LibraryAddedEvent
        → DirectoryWatchingService (register watcher)

startLibraryScan()
    → stored library operation, run by its scheduled task
        → finishing steps (check the library folder, remove orphaned files), then the end transaction
            → ScanEndedEvent, LibraryStatusChangedEvent (after the commit)

removeLibrary()
    → LibraryRemovedEvent
        → DirectoryWatchingService (unregister watcher)
        → StreamingSessionCleanupListener (terminate sessions)
----

Side effects triggered by transactional operations use `@TransactionalEventListener(AFTER_COMMIT)` to ensure they only execute after a successful commit. Non-transactional publishers use `@EventListener` for synchronous, same-thread delivery.

See https://github.com/streamarr/streamarr-adr/blob/main/adr/0010-spring-application-events.adoc[ADR 0010] for full rationale.

=== Persisted Probes and Worker Execution

https://github.com/streamarr/streamarr-adr/blob/main/adr/0032-media-file-probe-results-are-persisted.adoc[ADR 0032] persists container and stream data separately from title metadata.
Scans and watcher events schedule missing or outdated probes before skipping already matched files.
A scan finishes after matching and enrichment, and after every primary artwork request and probe it made has a recorded result.
A probe no longer belongs to the scan once a later change replaced its inputs, a newer probe version stored an outcome for the same source, or its file was removed.
A scan retries a failed probe at once and counts only a failure recorded after its own request, so a rescan after a share comes back waits for fresh attempts; playback requests keep the backoff.
Person and company artwork and the later retries of failed probes continue after the scan.
Playback reads stored outcomes.
When a file has no usable outcome, playback moves the file's probe to the front of the queue.
Due probes run by priority, then by execution time, and the playback request raises its probe's priority without changing the probe's execution time or backoff.
After the playback request commits, the scheduler checks for due probes at once, so the probe starts without waiting for the next poll.
Playback then waits for the outcome, up to `streaming.probe-wait-limit`, and wakes when an attempt at the probe ends.
The limit counts elapsed time, so a step of the system clock does not lengthen the wait. When the limit passes without an attempt end, playback reads the stored outcome once more and returns.
It returns a typed not-ready error when no compatible worker is connected, when an attempt after the request fails, or when the wait reaches the limit.
The probe keeps running in each case.
Playback returns a typed failure for a retained terminal media error.
When the video must be encoded and the probe recorded no usable frame rate, it returns a typed frame-rate error instead of starting a stream session, because workers encode at the probed frame rate.
A stream copy of the same file still plays.

Each probe version reports every fact of the versions before it.
Version 3 adds the keyframe positions of the chosen video stream.
Version 4 adds the facts that playing HDR and 10-bit sources as SDR needs: the dynamic range, bit depth, chroma subsampling, rotation and codec string of each stream, the chosen video stream, and the output frame rate.
Version 4 also adds the end time of each audio and video stream, where the container header states the end time.
Version 4 also adds the sample rate and profile of each audio stream, the container cropping of each video stream, and the container's chapters.
Version 4 also adds the HDR10 static metadata that the container declares for each video stream: the mastering display color volume and the content light level.
Version 4 also adds the title, the handler name and the hearing-impaired flag of each audio and subtitle stream.
Version 5 adds the codec profile, level, tier and color signaling of each video stream.
Version 5 also reads the first frames of the chosen video stream for HDR10+, Dolby Vision RPUs and where the samples place them, and the static HDR metadata that only the bitstream carries.
It also reports whether every packet that it read of that stream carries a presentation time.
For H.264 and HEVC the worker also walks the SEI messages of the stream's extradata and of the packets that it read, and for AV1 the metadata OBUs of the extradata and of those packets.
The walk skips each NAL unit that FFmpeg drops before its decoders see it, so such a unit is never an RPU, an SEI message or a slice.
The probe reports HDR10+ or an RPU as absent only when the frames show none, the walk read every unit that could hold one, and no nested SEI message or layer-specific metadata OBU holds one; otherwise the feature stays unknown.
For H.264 and HEVC it reports whether each RPU ends its own picture's sample, as Dolby Vision requires, or starts its sample.
Before version 57, mkvmerge started each picture's sample with the previous picture's RPU, and a file of that layout whose start was cut away also starts its first picture's sample with an RPU, so the probe reports that every RPU starts its sample whether or not the first picture's sample holds one.
The probe reports no placement when the first packets cannot tell it, and AV1 reports none, because an AV1 RPU belongs ahead of its frame.
An RPU that starts its sample rules out a copy; no placement does not.
An encode of an HEVC Dolby Vision source without a compatible base moves each RPU to the end of its picture's sample, where FFmpeg's decoder reads it, unless the probe found every RPU there already.
The encode takes an RPU that starts a sample as the previous picture's, with or without a placement.
The move copies the samples with their presentation times, and a copy of packets without them stamps each picture with its decode time and loses the pictures that B-frames reorder.
So the encode moves RPUs only when the probe saw a presentation time on every packet that it read; otherwise it reads the samples unchanged.
The usual source without presentation times is a raw HEVC stream.
FFmpeg's HEVC parser ends each of its packets just ahead of the next access unit, so an RPU that follows its picture's slices, where Dolby Vision places it, ends that picture's packet, and the decoder reads it.
The decoder still ignores an RPU that lies between the NAL units that begin an access unit and its first slice.
A source without a compatible base and without presentation times that places its RPUs there keeps every picture, but each picture loses its reshaping and shows the wrong colours; moving those RPUs would keep the colours but lose pictures, because the move's copy stamps each picture with its decode time.
For every other video codec the probe walks no units, so only the frames tell it a feature: it reports HDR10+ or an RPU when the frames show one, as VP9 frames in WebM carry HDR10+, but never reports HDR10+, an RPU or Dolby Vision as absent, and reports no placement.
An omitted flag on a mastering display or a content light level means that the stream carries, or may carry, that value although the probe left it empty, either because the probe could not read the value or because it could not rule the value out.
A stream with either flag set is never PQ10.
When the probe read no frames, an empty value means only that the container declares none, so it never proves PQ10.
Version 2 is unused.
The server requests version 5.
After the version rises, the server scans each library that holds a result of an earlier version at startup.
Playback keeps using a file's earlier result until the scan stores the file's new result.

https://github.com/streamarr/streamarr-adr/blob/main/adr/0033-transcode-worker-is-a-separate-service.adoc[ADR 0033] requires workers for probing, transcoding, and remuxing.
Each worker opens an outbound, long-lived gRPC `WorkerSession` over the server's single plaintext listener.
https://github.com/streamarr/streamarr-adr/blob/main/adr/0035-worker-uses-spring-boot-and-mesh-transport-security.adoc[ADR 0035] keeps colocated connections on loopback and requires mesh mutual TLS and worker ServiceAccount authorization for distributed connections.
The live connection owns registration, capacity accounting, commands, and job-attempt fencing.
Segment uploads use separate bounded HTTP/2 streams over the same channel.
Media is addressed by opaque `MediaSourceRef(source_namespace_id, relative_key)` values rather than host paths.
Administrators map each source namespace to the same media content on the server and its workers.

The supported topology has one Streamarr server and independently scalable workers.
Kubernetes workers run in a separate Deployment. The server uses stop-before-start replacement as specified by https://github.com/streamarr/streamarr-adr/blob/main/adr/0027-library-work-claimed-in-database-single-instance.adoc[ADR 0027].
Workers have no database access. The standalone Spring Boot worker exposes Actuator health checks on its management port.
The server image contains only the server application. Worker implementation code and FFmpeg packaging live in the standalone worker repository.
The server can start and remain ready with zero connected workers, but playback and probing require worker capacity.
Multi-server coordination remains deferred.

== Authentication and Invalidation

Identity, sessions, and token security follow
https://github.com/streamarr/streamarr-adr/blob/main/adr/0015-authorization-profiles-and-content-controls.adoc[ADR 0015] and
https://github.com/streamarr/streamarr-adr/blob/main/adr/0016-authentication-mechanisms-and-session-security.adoc[ADR 0016]: ES256-signed access
tokens with nested scopes, mandatory strict expiry, and digest-only rotating refresh tokens.
Ordinary API claims remain valid only until their short expiry; refresh revalidates live session,
account, and context authority. Playback additionally checks live authority on stream creation and
every playlist and segment request, as
https://github.com/streamarr/streamarr-adr/blob/main/adr/0018-live-playback-authority-and-outbound-workers.adoc[ADR 0018] specifies.
The browser client is same-origin by construction -- development
tooling proxies the API paths and production serves the client from the application origin --
so no CORS configuration exists and none should be added (recorded as a rejected alternative in
ADR 0016).

Tokens are signed with an EC P-256 key (`AUTH_TOKEN_SIGNING_KEY`, base64 PKCS#8; generate with
`openssl ecparam -name prime256v1 -genkey -noout | openssl pkcs8 -topk8 -nocrypt -outform DER |
base64`). Only the media server holds the private key; verifiers need public keys only, chosen
by the RFC 7638 thumbprint each token carries as `kid`. Rotation is two-phase so an HTTP cache
can never hide the incoming key: first add the new public key (base64 SPKI) to
`AUTH_TOKEN_VERIFICATION_KEYS` and restart -- it is prepublished in JWKS while the old key
keeps signing; then, after at least the JWKS `Cache-Control` window (5 minutes), configure the
new private key, replace the prepublished entry with the old public key, and restart --
outstanding tokens keep verifying until they expire. Skipping the prepublish wait risks
verifiers behind a shared cache rejecting newly signed tokens for up to the cache window,
because a refetch on unknown `kid` can be answered with the cached pre-rotation key set. A
blank signing key generates an ephemeral key pair at startup (tokens die on restart; sessions
recover through refresh).

ES256 exists because of the transcode split: horizontally scaled transcode workers running
FFmpeg are the most exposed tier and must never hold a token-minting secret. Signature
verification alone never authorizes a request, though -- revocation is authoritative state,
not signature checking. Playback revocation is one indexed live-authority query rather than token
counters or a persisted stream-session state machine. Workers never verify
playback tokens; the server remains the playback request gate and segment proxy.
The public verification keys are served at `/.well-known/jwks.json` (ADR 0016).

V049 removed the version claims, cache, PostgreSQL notification feed, counter columns, and
pooler-mode exception. Ordinary API tokens retain issued authority until strict expiry; refresh
checks the live authorization session and context, and every playback request checks live authority.

== Key Design Decisions

See https://github.com/streamarr/streamarr-adr/tree/main/adr[Architecture Decision Records] for detailed rationale. Summary:

|===
| Decision | Rationale

| PostgreSQL over SQLite/H2
| Production-grade, supports custom ENUMs, UUID primary keys, full-text search

| GraphQL over REST
| Flexible queries for rich tvOS client, Relay pagination for infinite scroll

| Keyset pagination over offset
| O(1) performance regardless of page depth

| ProcessBuilder + FFmpeg over JNI, in the worker
| Full control over process lifecycle, proven pattern (Jellyfin/Plex/Emby); the server itself starts no processes (https://github.com/streamarr/streamarr-adr/blob/main/adr/0033-transcode-worker-is-a-separate-service.adoc[ADR 0033])

| TDD and behavior testing
| Tests at service boundary are protocol-agnostic and survive refactoring

| TMDB metadata abstraction
| Provider interface allows future sources without changing the pipeline

| Spring Application Events
| Decouples side effects from core operations, eliminates circular dependencies (https://github.com/streamarr/streamarr-adr/blob/main/adr/0010-spring-application-events.adoc[ADR 0010])

| Stream decision architecture
| Per-stream decision records compose into TranscodeDecision; mode resolution considers all stream types (https://github.com/streamarr/streamarr-adr/blob/main/adr/0013-stream-decision-architecture.adoc[ADR 0013])
|===
